AIDA alert process

Alert review and rewrite overview

This report explains how AIDA reviews Canada.ca alerts, identifies issues, creates recommended rewrites, checks the results, and applies accepted changes back to the page. It is intended as a plain-language overview of the current alert process.

Process summary

  1. Find alerts
  2. Identify issues
  3. Rewrite selected alerts
  4. Check quality
  5. Patch the page

Alert review flow

The review flow is the first pass. Its job is to understand the page and report alert issues in a structured way.

What AIDA sends

AIDA starts from the page HTML and focuses the model on alert review. With compact context enabled, it sends structured page and alert signals. Without compact context, it sends sanitized alert HTML.

What AIDA gets back

The model returns alert issues with categories, severity, evidence, and recommendations. The user selects which issues should be included in the rewrite step.

Alert rewrite flow

The rewrite flow is a second pass. It uses selected issues and rewrites only the relevant alert containers.

Per-alert rewriting

AIDA maps selected issues back to their alerts. Alerts without selected issues are skipped. For selected alerts, AIDA creates a per-alert rewrite request using the original alert, the selected issues, link guidance, style guidance, compact context when available, and examples when enabled.

Safe page update

AIDA checks each model draft before applying it. A clean rewrite can be accepted directly. A draft with a narrow problem can be retried or repaired. If AIDA cannot produce a safe rewrite, it keeps the original alert.

What AIDA checks for

These are the main things AIDA checks before a rewritten alert can be applied to the page. The next section explains how AIDA responds when one of these checks needs action.

Structure

Valid alert HTML

The rewrite must be a complete alert wrapper with usable HTML structure.

Headings

Clear alert heading

The rewritten alert should include a short, descriptive semantic heading.

Links

Links stay controlled

AIDA checks that links are not invented, lost, converted to placeholders, or removed without a selected issue that supports it.

Wording

Text remains specific

The rewrite should address the selected issue without inventing facts or copying example wording.

Detailed guardrail logic

This section expands on the main checks. AIDA uses both preventive guidance and after-the-fact checks. The guidance steers the model before it writes. The checks decide what happens after AIDA receives a draft.

Preventive guidance

Key instructions for rewriting

  • Keep the edit inside the existing alert container.
  • Preserve the original meaning, facts, dates, program names, and source links.
  • Use short, plain, active, neutral wording.
  • Add or preserve a short descriptive heading.
  • Use examples as pattern guidance only, not wording to copy.
Hard checks

Reject unsafe drafts

  • Invalid or incomplete alert wrapper HTML.
  • New hyperlinks when the original alert did not have links.
  • Removed required links when link removal was not justified by the selected issue.
  • Example wording copied too closely into the rewrite, unless the example is also very close to the original alert.
Retry triggers

Ask again with a targeted correction

  • The returned HTML is not a full alert wrapper.
  • The rewrite does not include a semantic heading.
  • The rewrite adds, removes, or placeholders links incorrectly.
  • A standalone link sentence needs clearer lead-in handling.
  • The rewrite is too close to an example.
Local repair

Repair narrow, predictable problems

  • Restore one original link when a required link was dropped.
  • Remove unexpected anchors when no links were allowed.
  • Insert a missing heading when the rest of the rewrite is usable.
  • Clean standalone link punctuation after the closing anchor.
  • Repair embedded standalone lead-in paragraphs when the pattern is otherwise clear.
  • Preserve valid original standalone link lead-ins when the model changes them unnecessarily.
Fallback

Choose the safest final outcome

  • Model: the model rewrite passed the checks.
  • Local repair: AIDA accepted a repaired version of a close model answer.
  • Soft-failure candidate: AIDA used the safest close candidate when the remaining issue was low risk.
  • Passthrough: AIDA kept the original alert instead of forcing an unsafe rewrite.
Current rule source

Where the guardrails come from

Shared behavioural guidance comes from shared-rewrite-guidance.json. Retry text and runtime-specific rule fragments come from runtime-rewrite-rules.json. The broader rewrite contract comes from rewrite-instructions.json.

Options that affect the flow

Compact context

Smaller page summary

Compact context sends structured page and alert details instead of relying only on a larger HTML input. It helps focus issue analysis and can provide useful alert context during rewriting. In testing, this appears to be especially helpful with smaller AI models because they have less irrelevant page content to sort through.

Examples

Optional rewrite patterns

The examples option supplies selected rewrite examples to the model. AIDA records which examples were supplied and which ones the model says it used.
