AIDA topic doormat process

Topic doormat review and rewrite overview (in-progress)

This page summarizes how AIDA detects GCWeb topic doormats, sends structured doormat data to the issue prompt, asks the model for bounded classifications and editorial evidence, makes the final issue decisions in AIDA, and passes selected issue rows into the rewrite prompt when users ask AI to rewrite the doormat set.

Process summary

  1. Detect current and legacy topic doormat blocks.
  2. Extract link text, labels, destination, description, counts, language, and H2 section metadata.
  3. Fetch destination context and local IA child-page context when available.
  4. Run local deterministic checks for counts, link validity, structure, formatting, trailing description punctuation, list connector usage, repeated openings, Most requested duplicates, and IA review flags.
  5. Send the complete doormat set to the Topic doormats issue skill.
  6. Ask the model to classify every doormat using constrained values and grounded evidence.
  7. Let AIDA validate and aggregate the classifications, apply local decision rules, and build the displayed issues.
  8. Store selected issue rows for the current working HTML.
  9. When Doormats is selected in Send to AI, run the issue analysis if needed, compose the rewrite skill, and send current HTML plus selected issues and destination context for affected doormats.

Topic doormat review flow

The issue flow is set-based. AIDA sends all detected topic doormats together so the model can classify each item in context while AIDA keeps deterministic and classification-derived issue decisions local.

Input

What AIDA sends

AIDA sends structured doormat summaries, including page order, section-local order, link text, extracted labels, href, description, exact character counts, language, structure flags, and H2 section metadata. AIDA also sends label-stripped analysisLinkText and analysisDescription for destination meaning and content-coverage checks. For each resolved destination, AIDA supplies the HTTP status when available, page title, H1, introductory paragraphs before the first H2, all H2 headings, and destination label/status evidence.

Output

What AIDA gets back

The model returns required description-style, link-style, destination-relationship, relationship-basis, and destination-content classifications for every doormat. It may also return bounded candidate rows for the remaining model-owned editorial issues. These are structured inputs to AIDA, not the final displayed report.

Classification first, final decision in AIDA

For checks that depend on comparing doormats within a section or against a destination, the model performs the language judgment and AIDA owns the issue decision. This keeps semantic classification flexible without letting one model response directly determine section-level findings, thresholds, severity, or suppression rules.

1. Model classifies

Bounded labels for every doormat

The model must return values from defined enums, such as description style, link style, destination relationship and its basis, plus destination element coverage. It identifies meaning, grammatical construction, and important destination elements; it does not return locally owned issues such as length, punctuation, broken links, IA flags, content gaps, or section style mixes.

2. AIDA validates

Ground classifications in supplied data

AIDA checks the response shape, allowed labels, doormat indexes, destination element IDs, required reasons, destination status, label/status evidence, and available page context. Invalid, unsupported, or ungrounded classifications cannot create displayed issues.

3. AIDA decides

Aggregate and apply the rule

AIDA groups valid classifications by section or page, applies thresholds and deterministic safeguards, suppresses known false positives, assigns the configured severity, and creates the final issue rows shown to users.

Editorial exception

Model-owned judgment remains bounded

Some editorial issues cannot yet be derived from a stable local rule, such as genuinely ambiguous description wording or unjustified labels. The model may return those candidate issue rows directly, but AIDA still validates them against the taxonomy and response contract before displaying them.

Section rules

H2 headings define section-local numbering for the doormat limit and section-level style consistency.

Local structure

H2 sections reset numbering

AIDA assigns each topic doormat to the nearest preceding H2 section and numbers doormats from 1 inside that section.

Limit rule

Nine doormats per section

AIDA reports too-many-doormats-in-section once as a section-level issue when an H2 section has more than 9 doormats.

Style scope

Style checks stay within each section

AIDA aggregates link-name and description style classifications inside each H2 section.

How AIDA determines issues

The current flow separates model classification from AIDA decisions. AIDA owns exact checks, local IA review flags, and final classification-derived issue rules; the model supplies semantic classifications and handles the remaining model-owned editorial judgment.

Exact character counts

AIDA provides authoritative link text and description character counts and reports length issues locally. Extracted labels and badges are excluded from link and description counts in both languages. When both languages are available, AIDA compares the English and French equivalent doormat and uses the longer count for severity.

Link names use a 45-character ideal threshold and 75-character maximum threshold: 46-60 is Low, 61-75 is Medium, and more than 75 is High. Descriptions use a 120-character threshold: 121-130 is Low, 131-140 is Medium, and more than 140 is High.

AIDA reports at most one link-length issue and one description-length issue per section. Evidence keeps English and French counts in separate severity-coloured pills. Link pills keep the ideal limit, such as FR 71/45; description pills show only the count, such as FR 133.

Doormat count limit

AIDA applies the 9-doormat limit per H2 section.

Structure and formatting

AIDA reports objective structure and formatting issues locally where the page markup already proves the issue, including split heading links, multiple links in one doormat, links inside descriptions, trailing punctuation, first- or second-person description openings, and legacy topic doormat markup.

Description trailing punctuation is handled deterministically in both the issue report and rewrite flow. When that issue is selected, AIDA removes only the final punctuation mark without asking the model to rewrite the wording for that issue.

AIDA also detects likely key-term descriptions that use and or et before final list items. English checks the comma-before-and pattern in comma-list descriptions. French also checks the normal A, B et C pattern. AIDA does not run the same check for or or ou.

Description and link style

The model classifies each description and link by grammatical construction. Link styles are topic, product-or-service, action, audience-group, or mixed-or-unclear. Description rewrite guidance uses leave-unchanged, retain-phrase, tighten-phrase, add-specificity, convert-to-keyword-list, or convert-to-task-list. AIDA groups link-style labels by H2 section and creates section-level mixed-style rows or individual outlier rows when warranted. Mixed-style issues are Low severity. AIDA does not report individual outliers when the whole section is already mixed.

For link-style classification, gerund link names such as Filing a trust return or Submitting documents online are treated as topic when they mean how to or instructions for the task. AIDA also normalizes model classifications so gerund, how-to, and who/what/when/where/why link names are not treated as imperative action links merely because the underlying subject is a task.

Destination relationship

The model classifies whether each link name is equivalent, accurately broader or narrower, materially different, or unavailable, and identifies the basis for that decision. AIDA compares the non-label link text with the destination title or H1 by meaning, not exact wording, ignores Canada.ca title suffixes, allows compatible wording shifts, and reports only grounded core-concept conflicts.

Doormat labels

AIDA extracts visible label and badge text from each doormat and destination label/status evidence from titles, H1s, intros, alerts, labels, badges, time elements, and date metadata. Original link text and descriptions remain available for display and evidence, but AIDA removes extracted labels from analysisLinkText and analysisDescription before destination matching and content-coverage assessment. Labels such as Closed, Formerly, Replaced, New, or Updated can be valid when they expose destination status before the user follows the link.

Broken links

AIDA reports broken-link locally for objective link failures such as empty or invalid hrefs and fetched destination HTTP error statuses. The model does not report this issue directly.

Doormat content gaps

The model classifies supplied destination elements as important, covered, or missing by ID. AIDA reports a content gap only when a missing important ID matches extracted page context and passes deterministic local guardrails.

  • AIDA rejects IDs that were not supplied in the extracted destination context or that the model also marked as covered.
  • AIDA suppresses English and French lifecycle/status/update text when it is already exposed by the visible doormat text or when it is not decision-critical.
  • AIDA suppresses generic H2 gaps when the same concept is already present in the doormat, such as Eligibility/Admissibilite already being represented by eligible/admissible, or by multiple concrete bilingual eligibility cues such as audience, age, income, disability, or family-care criteria.
  • AIDA suppresses broad intro-definition gaps when normalized tokens and bilingual concept groups show the doormat already covers the destination's program, payment, audience, eligibility, application, amount, deadline, or document concept.
  • AIDA still reports unmatched decision-critical concepts, such as an application, eligibility, deadline, amount, or required-document concept that is present in the destination context but not represented in the link text or description.
Repeated description openings

AIDA checks each H2 section locally for descriptions that begin with the same first two normalized words. It reports at most one section-level row per section when an opening affects at least 40% of the section, with Medium severity when affected doormats are adjacent or the pattern affects more than 60%.

Most requested duplicates

AIDA compares doormat links with Most requested links locally to identify duplicate destinations. URL fragments must also match.

Choice of doormats

AIDA compares doormat destinations with direct child pages from the IA crawl. Missing child pages become Medium review flags, and non-child-page doormats become Low section-level review flags. AIDA also adds child-page and page-view metadata to displayed doormat rows when available.

No issues rows

AIDA keeps every detected doormat visible, including clean items.

Fallback behaviour

AIDA preserves the configured fallback order, logs request and response metrics for topic doormat issue calls, repairs invalid JSON when possible, and builds local No issues rows if no usable model output is available.

For model-owned issue rows, AIDA also checks the displayed evidence and recommendation after parsing. Empty strings and dash-only placeholders are treated as missing. AIDA sends only those incomplete issue fields back to the model for repair. If the repair still does not provide usable text, AIDA keeps the issue row visible and displays No AI evidence was received. or No AI recommendation was received. for the missing field.

Anne's original categories

I outlined some possible doormat pain point categories. In bold is the potential category, sub-bullets contain the more detailed issue. Let me know if this helps or if you need something else.

  • Link code issue
    • Broken link
    • Misdirected link (wrong page or wrong anchored location)
    • More than one link
  • Link name
    • Lacks clarity (must provide clear choice)
      • Must be descriptive and unique on page
    • Too long (wordy)
      • EN ideally under 35 characters (with spaces)
      • FR ideally 45 characters (with spaces)
    • Too different from destination page title
      • Does not need to be exact match of destination page title, but should convey similar idea
  • Repeat link
    • Don't repeat links in Most requested
  • Description lacks clarity (unclear)
    • Missing needed information (content gap)
  • Description too long (too wordy)
    • EN should be under 90 characters?
    • FR under 120 characters?
  • Description has incorrect style (not sure of Marvin's wording on this)
    • Action verbs that summarize what can be done on the page
    • list of keywords that summarize information on the page
    • list of tasks that can be accomplished on the page
    • (We have examples of the style options in the UCDG Doormats – GCWeb design system)
  • Description formatting
    • Don't use "and" before the last item in the list
    • Don't use icons or images
    • No special formatting (bold, italics, bullets)
    • Capitalize the letter of the first word
    • Use commas to separate listed items or phrase
    • Do not put any punctuation at the end
    • No links in description
  • Enhancement label
    • Only for a recent change (e.g. info label "New", Danger label "Closed")
  • Choice of doormats
    • Direct child page missing from the doormats (Medium review flag)
    • Doormat destination outside the direct child pages (Low review flag)

Topic doormat rewriting

Used to guide rewritten topic doormat content, issue-aware rewrite priorities, destination evidence for affected doormats, and output format.

Rewrite guidance uses destination intent to preserve link framing. Imperative link names are appropriate when the destination lets users start, complete, or continue a task. Gerund, how-to, or explanatory link names are appropriate when the destination mainly provides information, instructions, requirements, eligibility, timing, or rules about the task.
